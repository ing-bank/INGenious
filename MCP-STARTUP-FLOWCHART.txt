FAILURE SCENARIOS & THEIR CAUSES
════════════════════════════════════════════════════════════════════════════════

Scenario A: "ENOENT: no such file or directory"
───────────────────────────────────────────────
  Problem: CLI executable not found
  
  ┌─ resolveCliPath() ─────────────────────────────────────┐
  │ Returns: /usr/local/bin/ingenious (doesn't exist!)    │
  └──────────────────────┬────────────────────────────────┘
                         │
                    ❌ FAILS HERE
                         │
  ┌─ cp.spawn() ──────────────────────────────────────────┐
  │ Error: ENOENT: no such file or directory              │
  │ Status: 'error'                                       │
  └────────────────────────────────────────────────────────┘
  
  Root Cause: Issue #1 - CLI Path Resolution
  Solution: Validate path exists before returning


Scenario B: "ClassNotFoundException" or "NoClassDefFoundError"
──────────────────────────────────────────────────────────────
  Problem: Java cannot find INGenious classes
  
  ┌─ expandedClasspath() ──────────────────────────────────┐
  │ lib/ directory doesn't exist                          │
  │ listFiles() returns null                              │
  │ No JAR files added to classpath                       │
  │ Returns: "" (empty string) ← WRONG!                   │
  └──────────────────────┬─────────────────────────────────┘
                         │
                    ❌ FAILS HERE
                         │
  ┌─ Java Process ────────────────────────────────────────┐
  │ java -cp "" com.ing.engine.core.Control ...           │
  │                                                        │
  │ Error: Could not find or load main class              │
  │ Exit Code: 1                                          │
  │ Status: 'error'                                       │
  └────────────────────────────────────────────────────────┘
  
  Root Cause: Issue #2 - Classpath Expansion
  Solution: Add validation for each classpath entry


Scenario C: MCP Server Exits with No Error Message
────────────────────────────────────────────────────
  Problem: Error happens but is silent
  
  ┌─ ServerCommand.call() ────────────────────────────────┐
  │ Exception thrown (e.g., OutOfMemoryError)             │
  │ verbose = false                                       │
  │ System.err.println("[mcp] fatal: " + e.getMessage()); │
  │ Stack trace NOT printed (verbose=false)               │
  └──────────────────────┬─────────────────────────────────┘
                         │
                    ❌ FAILS HERE
                         │
  ┌─ Parent Process ──────────────────────────────────────┐
  │ Sees: Process exited with code 1                      │
  │ No error message visible                              │
  │ Status: 'error'                                       │
  │                                                        │
  │ User has NO idea what went wrong!                     │
  └────────────────────────────────────────────────────────┘
  
  Root Cause: Issue #3 - Silent Process Crashes
  Solution: Always log errors, write to diagnostic file


Scenario D: MCP Initialization Timeout
────────────────────────────────────────
  Problem: Server takes too long to start
  
  ┌─ Java Startup ───────────────────────────────────────┐
  │ JVM startup: 15 seconds                              │
  │ Classpath expansion: 30 seconds                       │
  │ MCPServer init: 20 seconds                            │
  │ Total: 65 seconds ← EXCEEDS TIMEOUT                  │
  └──────────────────────┬────────────────────────────────┘
                         │
                    ❌ TIMEOUT FIRES
                         │
  ┌─ Client ────────────────────────────────────────────┐
  │ Waits 60 seconds for initialize response             │
  │ Timeout fires after 60s                              │
  │ Closes connection                                    │
  │                                                       │
  │ Error: MCP request 'initialize' timed out            │
  │ Status: 'error'                                      │
  │                                                       │
  │ But server was almost ready! (65s > 60s timeout)     │
  └────────────────────────────────────────────────────────┘
  
  Root Cause: Issue #6 - Timeout Too Short
  Solution: Make timeout configurable, increase default


Scenario E: Configuration Path is Wrong
─────────────────────────────────────────
  Problem: User sets invalid cliPath or javaHome
  
  ┌─ VS Code Settings ────────────────────────────────────┐
  │ "ingenious.cliPath": "/old/path/ingenious"            │
  │ (But it was uninstalled and moved!)                   │

                         │

  │ No guidance on what's wrong                           │
  └────────────────────────────────────────────────────────┘
  
  Root Cause: Issue #4 - Configuration Validation Missing
  Solution: Validate paths and Java version at startup

DEPENDENCY TREE
════════════════════════════════════════════════════════════════════════════════

CLI Path Validation (Issue #1)
  └─ Must succeed before: Java spawn
     Impact: If CLI not found, process never starts


Java Setup (Java Version Check)
  └─ Must succeed before: Java process execution
     Impact: Wrong Java version causes immediate failure


Classpath Expansion (Issue #2)
  └─ Must succeed before: Java main class execution
     Impact: Empty/invalid classpath causes ClassNotFoundException
  └─ Depends on: JAR directories exist and are readable


Configuration Validation (Issue #4)
  └─ Must succeed before: Process spawn
     Impact: Invalid settings cause startup failures
  └─ Depends on: Issue #1 and Java version check


Error Logging (Issue #3)
  └─ Must succeed during: Exception handling
     Impact: Without logging, impossible to debug
  └─ Depends on: Issue #5 (stderr capture)


Stderr Capture (Issue #5)
  └─ Should succeed during: Error logging
     Impact: Enables remote diagnostics
  └─ Depends on: Environment variable set by Copilot SDK


Timeout Configuration (Issue #6)
  └─ Must succeed during: Client initialization
     Impact: Too short timeout causes false failures on slow machines
